# Універсальне розпізнавання інтерфейсу Dota 2

**Дата:** 2026-09-14
**Статус:** затверджено до реалізації
**Під-проєкт:** B з трьох (A — збірка та розповсюдження, C — автовибір ролі та героя)

## 1. Контекст і проблема

Dota Ready Helper працює лише на конфігурації автора: 1920×1080, російський клієнт,
повноекранний режим на основному моніторі. Причина — чотири PNG у `assets/`,
вирізані з цього конкретного екрана.

Що ламається у чужого гравця:

- **Роздільна здатність.** `pag.locateOnScreen` шукає точний збіг пікселів.
  На 2560×1440 інтерфейс Dota більший приблизно в 1.33 раза, збігу не буде за
  жодного значення `confidence`.
- **Мова клієнта.** Три з чотирьох шаблонів містять текст («ПОИСК ИГРЫ»,
  «ПРИНЯТЬ»). Англійський клієнт має інші слова та іншу ширину кнопок.
- **Масштаб інтерфейсу.** Повзунок розміру UI у налаштуваннях Dota змінює розмір
  кнопок незалежно від роздільної здатності, тому формула «шаблон × висота
  екрана / 1080» його не покриває.
- **Кілька моніторів і віконний режим.** `pag.size()` повертає лише основний
  екран, а `get_center_region()` рахує центр саме його. На машині автора
  віртуальний робочий стіл — 2560×2304 зі зсувом (−254, −1440): якщо Dota
  опиниться на другому моніторі, бот дивитиметься в порожнечу. Це вже зламано,
  а не гіпотеза.

Єдина частина, що переживає чужі налаштування, — пошук кнопки «Прийняти» за
кольором (`find_green_button`), бо він не залежить ні від мови, ні від розміру.

## 2. Цілі та межі

**Мета:** програма працює у гравця з будь-якою роздільною здатністю, мовою
клієнта, масштабом інтерфейсу та розташуванням вікна.

**У межах:**

- прив'язка координат до вікна Dota замість екрана;
- калібрування на машині користувача: шаблони знімаються з його клієнта;
- самокалібрування кнопки «Прийняти» під час першого знайденого матчу;
- діагностичний пакет для розбору поламок у користувачів;
- стан `NO_GAME` і відповідне зниження навантаження.

**Поза межами (окремі під-проєкти):**

- збірка `.exe`, автооновлення, публікація релізів — під-проєкт A;
- автовибір ролі та героя — під-проєкт C;
- переїзд даних до `%LOCALAPPDATA%` — див. розділ 8.

## 3. Архітектура

Три нових модулі, кожен з однією відповідальністю.

### `dota_window.py` — де Dota на екрані

```python
@dataclass(frozen=True)
class WindowInfo:
    left: int; top: int; width: int; height: int; title: str

find_window() -> Optional[WindowInfo]
is_usable(window) -> bool
capture(window) -> Image
to_absolute(window, rel_rect) -> tuple[int, int, int, int]
to_relative(window, abs_rect) -> RelRect
```

- Пошук вікна — **точний** збіг заголовка `Dota 2`. Пошук за підрядком «Dota»
  знаходить власне вікно налаштування програми (перевірено 2026-09-14).
- Додаткова перевірка імені процесу `dota2.exe` через `ctypes`
  (`GetWindowThreadProcessId` + `GetModuleBaseNameW`), без нових залежностей.
  Якщо перевірку виконати не вдалося — працюємо за заголовком і пишемо це в лог.
- Знімок — `ImageGrab.grab(bbox, all_screens=True)`. `pyautogui.screenshot`
  не вміє від'ємних координат другого монітора.
- Згорнуте вікно Windows повідомляє координати близько −32000; `is_usable`
  відсікає такі та вироджені прямокутники.

### `calibration.py` — як виглядає Dota у цього користувача

```python
@dataclass
class Element:
    file: str; rect: RelRect; source: str; captured_at: str

class Calibration:
    load(directory) -> Calibration
    save() -> None
    element(name) -> Optional[Element]
    search_region(name, window) -> Optional[tuple]
    is_stale(window) -> bool
    scale_to(window) -> None
```

Робота з даними: без UI і без комп'ютерного зору.

### `calibration_wizard.py` — вікно калібрування

PyQt6-потік знімання мірок. Окремо від `setup_dialog.py`: той збирає токен,
цей знімає екран, і файл налаштування вже наближається до 400 рядків.

### Зміни в наявному коді

- **`image_recognition.py`** втрачає знання про те, *що* шукає. Лишаються чисті
  операції над зображеннями: `find_template(needle, haystack, confidence)`,
  `find_green_button(image, offset)`, кліки. Знімок екрана більше не робиться
  всередині — він приходить ззовні, що прибирає підміну `pag.screenshot` у тестах.
- **`dota_helper.py`** замість `IMG_SEARCH_BTN` та `get_center_region()` бере
  шаблон і область пошуку в `calibration`, а координати — у `dota_window`.
  Додається стан `NO_GAME`.
- **`config.py`** більше не єдине джерело шляхів до зображень. Ключі
  `ACCEPT_REGION_WIDTH` / `ACCEPT_REGION_HEIGHT` стають зайвими: область
  рахується від вікна. Залишки цих ключів у чужих `.env` ігноруються без помилки.
- **`main.py`** отримує другий крок старту та два прапорці: `--calibrate`,
  `--diagnose`.
- **`assets/*.png`** лишаються, але використовуються лише всередині майстра як
  один із способів автопідказки.

### Потік запуску

```
main.py
 ├─ ensure_configured()        токен і chat ID            (готово)
 └─ ensure_calibrated()
      ├─ калібрування є і розмір вікна збігся   →  далі
      ├─ розмір змінився                       →  масштабувати шаблони
      └─ немає                                 →  майстер  →  зберегти / пропустити

DotaHelper.run()
 └─ один знімок вікна за ітерацію  →  усі перевірки на цьому кадрі
```

Один знімок за ітерацію — окрема зміна: зараз цикл робить до трьох
повноекранних знімків кожні 0.3 с.

## 4. Формат калібрування

Не всі елементи можна показати на вимогу:

| Елемент | Коли видно | Знімається в майстрі |
|---|---|---|
| `search_btn` | головне меню | так, одразу |
| `searching` | під час пошуку | так, після запуску пошуку |
| `stop` | під час пошуку | так, тим самим кадром |
| `accept` | лише коли матч знайдено | **ні** |

Вікно прийняття неможливо викликати на замовлення. Тому `accept` не питається
в майстрі: він шукається за кольором (цей детектор уже написаний і не залежить
ні від мови, ні від розміру), а **під час першого спіймання попапа кнопка
вирізається і зберігається як особистий шаблон**. З другого матчу працює точний
збіг, пошук за кольором лишається підстрахуванням. Калібрування відбувається
само, без жодного питання.

```
calibration/
  calibration.json
  search_btn.png  searching.png  stop.png
  accept.png        ← з'являється після першого знайденого матчу
```

```json
{
  "version": 1,
  "window": { "width": 1920, "height": 1080 },
  "elements": {
    "search_btn": {
      "file": "search_btn.png",
      "rect": { "x": 0.741, "y": 0.823, "w": 0.171, "h": 0.045 },
      "source": "auto",
      "captured_at": "2026-09-14T01:20:00"
    }
  }
}
```

- `rect` — частки клієнтської області вікна, тому місце кнопки переноситься на
  будь-яку роздільну здатність.
- `source` — як елемент потрапив у файл; потрібне для діагностики:
  `auto` (майстер знайшов сам), `manual` (гравець виділив рамкою),
  `shipped` (збігся наш готовий шаблон), `opportunistic` (вирізано під час
  першого спійманого матчу), `scaled` (перезбережено після зміни розміру вікна).
- `window` — розмір вікна на момент знімання; за ним визначається застарілість.
- Пошук іде не по всьому вікну, а в області навколо `rect`, збільшеній у
  `SEARCH_MARGIN = 2.5` раза і обрізаній межами вікна.
- `version` — файл іншої версії відкидається з повідомленням, а не валить програму.

**Застарілість.** Якщо розмір вікна не збігся, шаблони мають хибний розмір у
пікселях. Жорстко вимагати перекалібрування — грубо: гравець змінив роздільну
здатність на вечір і втратив робочу програму. Тому шаблони масштабуються за
відношенням розмірів вікна і пробуються; збіг — тихо перезберігаємо в новому
розмірі (`source` стає `scaled`). Стійка невдача — одне повідомлення в Telegram
«схоже, інтерфейс змінився, запусти калібрування», без зупинки роботи. Патчі
Dota, що змінюють вигляд кнопок, лікуються тим самим шляхом.

## 5. Потік калібрування

Вікно майстра і вікно Dota не можуть бути на передньому плані одночасно, тому
знімок робиться глобальною гарячою клавішею **F10** (`keyboard` уже в залежностях).

```
Крок 0.  Майстер чекає вікно Dota 2
         немає вікна → «Запусти Dota 2», перевірка кожні 2 секунди

Крок 1.  «Перемкнись у Dota, відкрий головне меню і натисни F10»
         F10 → знімок вікна → майстер повертається на передній план

Крок 2.  Автопошук на знімку:
           ├─ наші готові шаблони в діапазоні масштабів 0.5–2.0
           └─ пошук за кольором і формою
         один кандидат  → рамка на знімку: «Це кнопка пошуку гри?» [Так] [Виділю сам]
         кілька         → пронумеровані, гравець обирає
         нічого         → одразу ручний режим

Крок 3.  Ручний режим: знімок у вікні, виділення рамкою мишею,
         збільшений передперегляд вирізаного шматка для підтвердження

Крок 4.  «Натисни в Dota пошук гри і знову F10»
         з одного кадру знімаються `searching` і `stop`

Крок 5.  Збереження, зведення з усіма вирізаними кнопками,
         кнопка «Перевірити зараз» → свіжий знімок, звіт що знайдено
```

Крок 5 обов'язковий: майстер не заявляє про успіх, а перевіряє себе на живому
екрані. Інакше про невдале калібрування гравець дізнається лише тоді, коли бот
мовчки не прийме матч.

На фінальному екрані — рядок про те, що «Прийняти» визначиться автоматично при
першому матчі, щоб не здавалося, ніби елемент забули.

**Кнопку «Пропустити» передбачено навмисно.** Приймання матчів працює за
кольором і калібрування не потребує. Пропуск лишає головну функцію і вимикає
лише дистанційний запуск та зупинку пошуку — про що сказано прямо, без
замовчувань. Бар'єр першого запуску падає до нуля.

Повторне калібрування — `python main.py --calibrate` і автоматична пропозиція
після зміни розміру вікна.

**Краї:**

- **Ексклюзивний повноекранний режим.** Знімок часто виходить чорним. Майстер
  перевіряє кадр на майже повну чорноту і просить перемкнутися у віконний без
  рамки, а не знімає порожнечу мовчки.
- **Згорнута Dota** — ловиться `is_usable` до знімка.

## 6. Поведінка під час роботи

| Ситуація | Поведінка |
|---|---|
| Вікна Dota немає | стан `NO_GAME`, опитування раз на 2 с замість 0.3 с, у меню Telegram «Dota не запущена» |
| Dota згорнута | те саме |
| Калібрування пропущено | приймання працює; на «Запустити пошук» приходить «потрібне калібрування», а не «не знайшов кнопку» |
| Розмір вікна змінився | шаблони масштабуються; при стійкій невдачі одне повідомлення, робота триває |
| Патч змінив інтерфейс | той самий шлях |
| Елемент не знайдено на запит | попередження в Telegram + анотований знімок у `logs/` |
| Знімок не вдався (RDP, блокування) | спіймати, залогувати, збільшити паузу; цикл не падає |
| Клік не спрацював | уже зроблено: зараховується як пропуск + попередження |

Стан `NO_GAME` — не косметика: з нього немає переходу в `SEARCHING` за хибним
спрацюванням, а меню Telegram перестає пропонувати кнопки, які все одно не
спрацюють.

### Діагностика

Тестових машин немає, тому потрібен спосіб розібрати чужу поламку без тижневого
листування. `python main.py --diagnose` збирає у `.zip`:

- версію програми, версію Windows, перелік моніторів і роздільних здатностей;
- прямокутник вікна Dota;
- зведення калібрування: розмір вікна, `source` кожного елемента;
- результат пошуку кожного елемента просто зараз;
- анотований знімок вікна з рамками знайденого.

**Токен бота і вміст `.env` не потрапляють до архіву за жодних умов.** У архіві
є знімок гри, на якому видно нік у Steam, а іноді список друзів, тому перед
пакуванням програма прямо про це каже і відкриває теку, щоб гравець побачив
вміст до відправки.

## 7. Тестування

**Шар 1 — модульні тести, у CI.** Чиста логіка без екрана і без Qt: збереження
та читання калібрування, перерахунок часток у пікселі й назад, визначення
застарілості, відмова від файла чужої версії, вироджений прямокутник згорнутого
вікна, від'ємні координати другого монітора. Окремим тестом — точний збіг
заголовка вікна: пошук за підрядком «Dota» знаходив власне вікно програми.

**Шар 2 — синтетичні макети.** Прийом, який уже спрацював для кнопки «Прийняти»:
малюємо макет інтерфейсу через PIL і перевіряємо детектор на ньому. Тут ширше:
той самий макет у 1920×1080, 2560×1440, 1366×768 і 3440×1440, з підписами
російською, англійською та українською, зі збільшеним і зменшеним масштабом UI.
Ключовий тест — калібрування знято на одній конфігурації, розпізнавання йде на
іншій: це перевіряє математику масштабування. Плюс «шумний» макет з портретами
героїв, банерами і зеленим текстом, на якому не повинно знаходитись нічого.

Цей шар **не** доводить, що справжня Dota виглядає як макет. Він перевіряє наші
алгоритми, а не реальність.

**Шар 3 — ручна матриця на машині автора.** Єдині справжні дані:

| Конфігурація | Що доводить |
|---|---|
| 1080p без рамки, RU | базовий шлях: калібрування + реальний матч |
| той самий клієнт англійською | майстер працює з чужою мовою |
| 1280×720 у вікні, без перекалібрування | шлях масштабування шаблонів |
| повзунок масштабу UI на максимум | підлаштування або коректна пропозиція перекалібруватись |
| Dota на другому моніторі | прив'язка до вікна |

Кожен знімок з ручного прогону зберігається в набір тестових даних. Реальні
пікселі справжньої Dota в чотирьох конфігураціях — корпус, на якому майбутні
зміни ганяються офлайн. Діагностичний архів від користувача поповнює той самий
корпус, тобто кожен баг-репорт стає регресійним тестом.

Матриця лежить у репозиторії як чек-лист `docs/testing-matrix.md`.

**Готовність під-проєкту B:** ручна матриця пройдена, синтетика і модульні тести
зелені в CI, діагностика видає придатний архів, наявні 86 тестів не зламані.

## 8. Відкладені рішення

- **Розташування даних.** `calibration/` ляже поруч із програмою, як зараз
  лежать `stats/` і `logs/`. Для `.exe`, встановленого в Program Files, запис
  туди заборонений. Правильне місце — `%LOCALAPPDATA%`, але переїзд стосується
  логів, статистики й налаштувань, тому належить до під-проєкту A.
- **Правила Valve.** Автоприймання матчу — макрос у лобі. Під-проєкт C
  (автовибір ролі та героя) — уже втручання в ігровий процес, і ризик несуть ті,
  хто завантажить програму. Попередження в README має бути явним, а не виноскою.
